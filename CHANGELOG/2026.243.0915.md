# 2026.243.0915 — docs: stop pinning a CalVer in skill usage examples

## Summary

A usage example inside this repo's skill document pinned a hardcoded CalVer, e.g.:

```yaml
# charly.yml -- typically used via sway-desktop composition
my-image:
  candy:
    - '@github.com/opencharly/layer-sway-desktop:v2026.243.0831'
```

That version is guaranteed to rot. It cannot be kept current without minting a release for
every documentation edit, and while it is stale it teaches a version nobody should copy. It
now reads `:vTAG`:

```yaml
my-image:
  candy:
    - '@github.com/opencharly/layer-sway-desktop:vTAG'
```

`:vTAG` never goes stale, and it fails fast if pasted literally — an unresolvable ref — rather
than silently building against a months-old pin. That matters here specifically because these
`content:` blocks are **skill documents read by agents**, where a stale-but-valid version is
the more dangerous of the two failure modes.

The candy's own CalVer advances because the skill content changed, and changed content must
ship under a new version rather than reuse a released one.

### Why this was found

An org-wide pin sweep kept reporting these repos as stale and never converged. The cause was
that the scanner counted refs inside `content:`/`description:` block scalars as dependency
edges. They are prose: charly never resolves them, so they were never part of the
`resolved to multiple versions` problem the sweep exists to fix — but they can never be
current either, so they re-flagged on every pass.

Worse, the false edges invented a dependency **cycle** that does not exist:
`layer-xfce4-terminal` appeared to pin `layer-sway-desktop` while `layer-sway-desktop` really
does pin `layer-xfce4-terminal`. Advancing either would have made the other stale forever. The
reverse edge was a usage example in prose.

## How tested

The rewrite is **block-scalar aware**, not pattern-matched, because a doc example and a real
pin are indistinguishable by shape — both render as `    - '@github.com/opencharly/x:vY'`.

Its safety property is an assertion, not a regex: the tool re-parses the file after writing
and **refuses to save** unless the set of refs the file RESOLVES is byte-identical before and
after.

**Control** — a file containing the same version string twice, once as a real pin and once in
prose:

```
$ python3 refs.py ctrl.yml          # resolving refs BEFORE
@github.com/opencharly/layer-sway-desktop:v2026.243.0831
$ python3 rewrite_prose.py ctrl.yml
ctrl.yml 1
$ python3 refs.py ctrl.yml          # resolving refs AFTER — unchanged
@github.com/opencharly/layer-sway-desktop:v2026.243.0831

$ grep -n 'layer-sway-desktop' ctrl.yml
13:                    - '@github.com/opencharly/layer-sway-desktop:vTAG'   <- prose, rewritten
16:            - '@github.com/opencharly/layer-sway-desktop:v2026.243.0831' <- real pin, untouched
```

Identical strings, only the prose one moved.

`charly box validate` on the final committed tree, with the binary this repo pins — exit code
read from charly directly, never through a pipe:

```
$ charly box validate
$ echo $?
0
```

## Rulebook compliance

- **R1 (RCA)** — traced from a sweep that would not converge, to a scanner counting prose as
  dependency edges, to the rotting CalVer that made prose permanently stale. Fixed at the
  cause in both the scanner and the documents.
- **R3 (no duplication)** — one placeholder convention, applied identically across every
  affected repo in this sweep.
- **R4 (no workarounds)** — the alternative was teaching the sweep to rewrite prose on every
  wave, which would mint a release for documentation churn forever.
- **R5 (delete legacy)** — the hardcoded CalVer is replaced, not left beside the placeholder.
- **R6 (git safety)** — feature branch, no force-push, no hook bypass.
- **R7 / R10 (prove the gate)** — validated on the final committed tree, with a control
  proving the rewrite cannot touch a resolving ref.
